The storage OS that scales in all directions

One image. One node to a cluster. Storage that grows in every direction.

FRAD boots a machine straight into a storage platform: operating system, storage stack, clustering, high availability and the management CLI ship and update as one product, so a small team can run a lot of storage. Watch a node become a cluster.

    Three ideas carry the product

    Up and down on one node, with ZFS

    Local disks join or leave a host-local pool one at a time, as stripe, mirror or raidz. A disk is evacuated before it is released, and a released disk is a clean block device, free to go to Ceph next.

    Out and in across nodes, with Ceph

    Multi-node FRAD is a Ceph cluster run by cephadm. Block, file and S3 object storage come from the same cluster. A node starts alone and grows into a cluster with no re-install; a node leaves after its disks drain.

    Updates without fear

    Base-OS patches, FRAD's own code and full firmware images each travel on their own channel. Root on ZFS with ZFSBootMenu keeps the previous boot environment one menu choice away.

    What is built, what is designed

    Implemented today

    • Root on ZFS with ZFSBootMenu; UEFI install from ISO, USB or PXE, including UEFI HTTP boot
    • The read-only /frbe dataset holding all FRAD binaries, scripts and the SDK
    • One first-boot screen: a proposed configuration, one press to apply; an unattended mode for fleets
    • Single node to cluster growth by node join; control group promotion in one step; cluster discovery by mDNS
    • Host-local ZFS pool scaling per disk; Ceph via cephadm with block, CephFS and S3
    • Corosync, Pacemaker and HAProxy for the virtual IP, dashboard and S3 endpoint; cluster-wide checks and repairs
    • Per-install SSH keys, a per-cluster service secret and a cluster-wide admin password, all rotatable
    • PPU firmware image builds; Ceph container upgrades through cluster ceph_upgrade

    Designed, in progress

    • The apt channel behind a compatibility gate: an OS upgrade is refused if it would move the kernel, ZFS or podman past what /frbe was validated against
    • Boot environment clone, validate, then switch; rollback from ZFSBootMenu
    • /frbe versioning and fixpack packaging with a snapshot before every change
    • Fleet-wide rolling apply of updates
    • iSCSI gateway on cephadm

    Every step and feature above carries a built or designed chip. Nothing on this page is a benchmark or a forecast.

    How it is run

    Every command names its scope first, node or cluster, so an operator can tell from the command what it touches. A cluster command run on any member acts on the whole cluster and is safe to run again: a member that was unreachable is picked up the next time.

    Engineering notes

    FRAD comes out of problems met in production. The author writes them up on a personal engineering blog; three posts cover ground this page only summarises.

    Ceph orchestration pitfalls

    Moving Ceph from native daemons to cephadm, and making it work air-gapped: the registries, mirrors and defaults that are hard-coded along the way.

    Don't want to miss a ball with OpenCVE

    A self-hosted CVE feed built into a CI pipeline, so security updates are noticed in time. The same need drives FRAD's update channels.

    A power editor in initramfs

    Fitting a real editor into a boot-time filesystem where every megabyte counts. The kind of appliance-image work FRAD's installer is made of.
